# 图片对比（image-compare）

一个 macOS / Windows 桌面小工具，三个视图常驻一个窗口，左侧竖排导航或 ⌘1/⌘2/⌘3 切换：

| 视图 | 干什么 |
|---|---|
| **图片对比** `compare` | **三档布局**：1 图（单图浏览）/ 2 图并排 / 4 图 2×2，同步缩放/平移、适应窗口、100% 实际像素。布局、是否同步、滚轮行为都在工具栏「设置」抽屉里，**存盘、重启后恢复**（第九节）。走系统「打开方式」、拖文件进窗口，或**单击空窗直接把剪贴板里的图粘进来**；⌘C 复制当前图，粘进微信/Word 就是图片、粘进 Finder 是文件；载入一张带本机路径的图就会**列出它所在文件夹的全部图片**（左侧浏览侧栏，点一行、`↑`/`↓` 选一行或 `[`/`]` 翻页都是**选中哪行就显示哪一张**，**两图/四图布局下前后两张自动落在 A/B 上对照，单图布局下就换掉那一张**，见第八节） |
| **局域网传输** `transfer` | 自己的「文件传输助手」。可以给多台已登记的对端分别发文字、文件、文件夹，**一台还能开好几个对话框**（左边一列会话栏，一个框一行）；名字、大小、进度、收发历史都画成气泡，跨日插一条年月日分隔线；**跟微信一样首屏只看最近 10 条**，滚到顶（或点顶栏）再往前翻页；拖进来或 ⌘V 粘进来的东西即发（多台混用见第五节） |
| **文字收藏** `fav` | 三级树（分类 / 子分类 / 条目）记笔记，可复制全文、发到当前会话、直接在对比视图里打开；焦点不在输入框时 ⌘V 粘文字会自动开一个条目接住 |

**可以同时登记多台**：每台都能主动发，而且**同一台可以反复新建对话框**（「＋ 新聊天」里再点一次那台）；
没配对过的设备发消息进来会自动建会话并计未读，不会丢东西。
没有群发、也不做中转（一条消息只落到一个对话框里）。
会话的主键是**会话自己的 ID**，不是对端 ID —— 一个对话框在两边是同一个，靠线上带 `X-Session` 保证（见第五节）。
**所有数据只存本机**，不跨设备同步、不上云（设计已确认）。

## 一、数据存在哪

数据目录由 Tauri 的 `app_data_dir` 决定，也就是应用标识 `cn.aibbl.image-compare`：

- **macOS**：`~/Library/Application Support/cn.aibbl.image-compare/`
- **Windows**：`%APPDATA%\cn.aibbl.image-compare\`（按标识推导，尚未在 Windows 实机复核）

目录下八个东西：

| 名字 | 是什么 | 写法 |
|---|---|---|
| `device.json` | 本机身份：`id` / `secret` / `name` / `passphrase`。**配对口令是明文存本地**，删掉它就等于换了台新设备 | 原子写（先写 `.xxx.tmp-*` 再 rename） |
| `peers.json` | 登记过的对端**数组**（每台：名称、备注名、IP、端口、在线状态、last_seen）+ 一份解绑名单 `ignored`。一台一条，解绑只移那一条并把它记进名单 | 原子写 |
| `sessions.json` | 会话表：**一行一个对话框**，主键是会话自己的 `id`（一台的**基础对话** = 对端设备 ID，同一台再开的框 = UUID）、所属 `peer`、显示名、读指针 `read`，加上当前焦点 `active`（也是会话 ID）与被删过的 `hidden`。上一版没有 `id` 字段，读进来由 `normalize()` 按 `id = peer` 补齐 | 原子写 |
| `messages.jsonl` | 聊天历史，**追加式** JSONL：一次状态变化就追加一行。每行的 `peer` 是**对端设备 ID**（入向取签名里的 `X-Device`，不是本机绑定的那台），`sid` 是**归属的会话 ID**（空 = 那台的基础对话，所以老历史不用改写也不会丢）。读取时同一 `id` 取**最后**一行的内容、但按**首次出现**的顺序排列（不能因为更新了状态就跳到列表末尾），所以 sending→sent 只会显示最终态；翻页靠 `msg_history(limit, before, session)`：`session` 不传给全部历史（收藏视图用），传了就是那一个对话框的；`before` 不传给最近一页（默认 10 条），传了就是「这条之前再往前 N 条」，一页上限 500 | 只追加，不重写 |
| `favorites.json` | 三级收藏树，整份存成一个 JSON | 原子写 |
| `prefs.json` | 对比视图的界面偏好：`layout`（`"1"`/`"2"`/`"4"`）、`sync`（是否同步）、`wheel`（`"zoom"`/`"pan"`）。读的时候 `normalize()` 把脏值退回默认，**首启动没有这个文件，也不会自动写一个** | 原子写 |
| `inbox/` | 收到的文件与文件夹，见下 | 收完自动摊平 |
| `pastebox/` | 粘进界面但剪贴板里只有位图数据的东西（截图、微信里复制的图）落盘成真实文件的地方 | **只增不删** |

### 收件箱 `inbox/` 的形状（重要）

UUID 批次目录**只是传输途中的工位**：文件先落到 `inbox/<批次ID>/…`，收到最后一个文件（`X-Last`）后立刻把里面唯一的顶层条目挪到收件箱根：

```
inbox/
├── 微信图片_20261024.jpg      ← 单张图、单个文件，平铺在这里
├── 简历 (1).pdf               ← 重名不覆盖，自动加 " (1)"
└── 课程资料/                   ← 整个文件夹保持原来的子树结构
    └── 第一章/讲义.pdf
```

挪不动（权限异常等）就退回工位目录留着，绝不丢文件；多于一个顶层条目（正常不会发生）也原样留在工位目录里。

### 粘贴暂存 `pastebox/`

剪贴板里是**文件**时不往这里写（直接用原路径）；只有是**位图数据**（⌘⇧4 截图、微信里右键复制的图片）
才会落成一个文件，名字 `剪贴板图片-<时间戳>.png`，重名自动加 ` (1)`。
落在这里之后它就是一个普通本地文件：能预览、能发到当前会话、能另存为。

**同一份剪贴板内容反复粘只落一个文件**（按内容 sha256 认，只记最近一份）：
连着点四个空窗不会生四张一模一样的图 —— 以前会，看上去很像“粘不上/显示坏了”。

粘贴这条链路**不在运行时打日志**（排障期加的 `[clip] 剪贴板风味 / 字节数 / 落盘` 已拆掉）。
要看一次粘贴到底拿到了什么，跑只读探针（见第六节），它会把 `paste_paths` 的结果打出来；
要看剪贴板本身有什么类型，用 `osascript -l JavaScript` 列 `NSPasteboard.types`。

判“粘出来的是占位图标而不是图”的口径（手动看剪贴板时用得上）：
没有 `public.file-url`、而且位图尺寸是个整方的数（1024×1024 这类），
基本就是源只给了占位图标；粘十次会得到十张一模一样的图。

为什么不自动清：聊天气泡里的缩略图、`path` 字段指的就是这些文件，清掉就等于把历史消息里的图弄坏。
它们只来自你自己的粘贴，体积可控；真要腾空间就手动删整个目录（退出应用后再删）。

### 备份 / 迁移 / 清空

- **备份**：直接拷上面这八个东西即可，全是明文 JSON / JSONL，SQLite 之类一个都没有。`prefs.json` 不带也没关系，只是界面偏好回到出厂的两图 + 同步开。
- **换机器**：拷过去再改 `peers.json` 里那些对端的地址即可；口令一致就能继续互认。
  `sessions.json` 可以不带：首次启动会从 `peers.json` 与历史里的 `peer` 值重建会话，不带只是丢了读指针与改名。
  但多会话时代丢了它会更别扭：重建只会建出每台的**基础对话**，同一台那些另开的框只能以
  「补漏行」从历史里露出来（消息一条不少，但不挂未读、也不能改名），
  对方在那个框里再发一条才会正式建回会话行。要换机器就把这份一起拷走。
- **清空**：退出应用后删掉整个目录（下次启动会重新生成 `device.json`）。⚠️ 别在应用运行时删，会边写边丢。

## 三、跑起来 / 打包

```bash
npm install                      # 只装 @tauri-apps/cli

npm run dev                      # 开发：vite + rust 热重载
RUSTUP_TOOLCHAIN=stable-aarch64-apple-darwin npx tauri build --bundles app
```

> **Apple Silicon 必须显式指定 `stable-aarch64-apple-darwin`**，否则可能编出 x86 包、在 M 机上靠 Rosetta 跑或直接白屏。

发版要改**两处版本号**：`src-tauri/tauri.conf.json` 与 `src-tauri/Cargo.toml`（`Cargo.lock` 由 cargo 自动更新）。`package.json` 里的 `version` 只是 npm 元数据，不参与打包，当前仍是 `0.1.0`。

发布流程：

```bash
git tag -a v0.2.1 -m "说明"
git push origin main && git push origin v0.2.1   # tag 触发 CI 出双平台包并建 Release
```

CI 里 `RELEASE_TAG` 非空才创建 Release；只推分支不带 tag 时产物只进 Artifacts。GitHub Actions 之外本机没有别的发版通道（本仓库走 SSH，HTTPS 不可用）。

### 验证手段

```bash
cd src-tauri && RUSTUP_TOOLCHAIN=stable-aarch64-apple-darwin cargo test --lib   # 单元测试（含收件箱摊平、剪贴板落盘命名与 file URL 解码、解绑名单与备注名口径）
node tools/zoom_math_check.js                                                   # 对比视图零回归
node tools/paste_route_check.mjs                                                # 粘贴分流：什么时候该抢、抢来交给谁
node tools/session_route_check.mjs                                              # 会话路由：同一台多框、未读、分页游标不串
node tools/folder_browse_check.mjs                                              # 文件夹浏览：列表口径、A/B 交替落窗、小图内存闸门
node tools/prefs_layout_check.mjs                                               # 三档布局与系统设置：联动、存盘、单图浏览、CSS/HTML 合约
node tools/net_selftest.mjs                                                     # 端到端协议自检
```

剪贴板这两头都没法在普通单测里跑（要碰真的系统剪贴板），所以另有一个真机探针：

```bash
cd src-tauri && cargo test --lib -- --ignored clip::real_clipboard   # 读一次剪贴板，再把一张真 PNG 写回去
cd src-tauri && cargo test --lib -- --ignored clip::只读剪贴板探针 --nocapture  # 只读：打印 paste_paths 拿到了什么，不碰剪贴板
osascript -e 'set the clipboard to (POSIX file "/某张/图.png")'                  # 备料：当文件复制
osascript -e 'set the clipboard to (read (POSIX file "/某张/图.png") as «class PNGf»)'  # 备料：当位图
```

它会打印读到/写了什么。「只有位图、没有文件」这一岔要单独备料：osascript 往剪贴板放图时会顺手
补上一堆派生类型，public.png 永远存在，试不到 TIFF 分支；用 `onlytiff.js` 直接只声明 TIFF 一种：

```bash
sips -s format tiff 某张.png --out 某张.tiff
osascript -l JavaScript tools/clip-win-check/onlytiff.js 某张.tiff   # 注意：会盖掉用户当前剪贴板
```

探针跑完会把剪贴板换成它自己那张 1x1 图，要还原成用户原来那张：

```bash
osascript -l JavaScript tools/clip-win-check/restore_clip.js 原来那张.png
```

复制出去到底挂上了哪几味，直接列剪贴板看（两味都在才算对）：

```bash
osascript -l JavaScript -e 'ObjC.import("AppKit");var t=$.NSPasteboard.generalPasteboard.types;var o=[];for(var i=0;i<t.count;i++)o.push(ObjC.unwrap(t.objectAtIndex(i)));o.join("\n");'
# 期望看到 public.file-url 与 public.png 同时存在
```

**但只列 pasteboard 级的 types 不够**（它是把所有 item 的类型拉平去重），两味分在两个 item 上时
上面这段看起来一模一样，而实际粘出去会插两张同样的图（#24）。要数 item 个数得跑探针，
它会把 item 数、每个 item 的类型、以及「回读能不能拿到原路径」全部核一遍：

```bash
cd src-tauri && cargo test --lib -- --ignored clip::real_clipboard --nocapture   # 会盖掉当前剪贴板
# 期望：共 1 个 item，item#0: ["public.file-url", "public.png"]，且回读拿到原路径
```

落盘结果用 `file` / `sips` 看一眼是不是张完整 PNG（本次实测 68944 字节的 TIFF 转出了 6803 字节的 128×128 PNG）。

`net_selftest.mjs` 三种用法：

```bash
node tools/net_selftest.mjs                            # 打本机，口令从 device.json 读
node tools/net_selftest.mjs <配对口令>                  # 打本机，显式给口令
node tools/net_selftest.mjs <口令> --host 192.168.1.20  # 打另一台，只看状态码
```

它覆盖：未签名 403、错口令 403、正确签名 200、`/msg` 落库、中文子目录流式 PUT 字节一致、
sha256 不符 422 不留残档、四种路径穿越全 400、单文件摊平成 `inbox/<名字>`、重名加 `(1)`、
文件夹整批大小与子树搬迁；倒数第二段「两个身份打同一台接收端」：落库的 `peer` 必须是签名里那个
`X-Device`（不是本机绑定的那台），两个身份各占一行会话、同一身份不会多出第二个框；
最后一段「同一台靠 `X-Session` 分落好几个框」：不带 `X-Session` 落基础对话（上一版兼容）、
本机没见过的会话 ID 被认下来、`/msg` 与 `/file` 同一个 `X-Session` 落同一个框、
同一台三个框各存各的、新框名字取 `X-Session-Name` 且对端后来改名不会覆盖本机、
以及拿别人的会话 ID 塞消息会落回自己这台的基础对话。
脚本自己登记并清理写进收件箱的测试文件，`messages.jsonl` 不动（条目都带「自检」字样），
但这两段会在会话列表里留下几行（本机身份、「自检乙机」与两个话题框），跑完在界面上删掉即可。

⚠️ **跑之前确认没有任何实例还在跑**：应用启用了单实例插件，第二个进程只会把参数交给已运行的实例然后立刻退出
（还会把对方窗口顶到前台），你的请求实际会打到那台正在运行的实例上，表现为口令不匹配的一堆 FAIL。
**绝不要**为了「干净环境」去删应用数据目录 —— 那里是真实聊天记录与收件箱，删了不可恢复。

不想把自检的假消息写进真实历史，就把整个运行环境挪到 /tmp（数据目录由 `app_data_dir` 推导，跟着 HOME 走）：

```bash
D="Library/Application Support/cn.aibbl.image-compare"
SB=/tmp/xfer-sandbox-home
mkdir -p "$SB/$D"
cp "$HOME/$D/device.json" "$SB/$D/"          # 只借口令与设备身份，历史与会话都不带走
HOME="$SB" ./src-tauri/target/debug/image-compare &   # 窗口会弹一下，数据全落 /tmp
HOME="$SB" node tools/net_selftest.mjs                # 两边都要带上同一个 HOME
kill %1; rm -rf "$SB"
```

沙盒里没 peers.json 也没 messages.jsonl，首次启动的迁移什么都不会建（新装就是这个空状态）；
自检产生的历史与会话都在 /tmp 里，跑完整个目录删掉就干净了。

## 四、局域网这一套的约定

页面 origin 是 `ipc://localhost`，在 webview 里直接 `fetch` 局域网地址会被混合内容策略与 CSP 双重拦掉，
所以**网络全部实现在 Rust 侧**，前端只 `invoke` + `listen`，不新增任何 capability 权限。

- **端口**：默认 `45789`，被占用时依次 +1，最多试 10 个。每台机器各自监听，实际端口在连接面板上显示。
- **发现**：mDNS 广播并浏览 `_imagecmp._tcp.local.`。公司网络 / VPN 常屏蔽 mDNS，看不到设备就用「手动 IP」绑定。
  注意 macOS 上主机名必须以 `.local.` 结尾（带尾点），否则 mdns-sd 注册会失败。
- **解绑不等于拉黑入向**：解绑那台会记进 `peers.json` 的 `ignored`，心跳从此不再把它自动登记回来（它仍留在
  「已发现」候选里，点一下才算亲手重新添加；手动 IP、重新探测同样算）；但它发过来的消息照收、
  照归到原来那个对话框。为什么必须有这份名单见 #25。
- **一台设备在界面上只有一个名字**：`Peer::display_name()` = 备注名 > 对方上报的设备名 > 露一截设备 ID。
  备注名只存本机、不参与签名、也不发给对端（对端那份名字归它自己维护），见 #26。
- **鉴权**：请求头 `X-Device` / `X-Ts` / `X-Sig`，签名 = `sha256(口令|设备ID|时间戳|body摘要)`，时间窗 ±300 秒。
  **未设口令时一律 403**，避免误把开放端口当传文件通道。服务端**不校验发送方是不是本机绑定的那台**：
  `X-Device` 伪造过不了签名，所以入向消息的 `peer` 直接取它 —— 这条是「谁发来的就归到谁的会话」的地基。
  同一台的几个框靠头上的 `X-Session` 分（它不进签名，只分落点与起名）。
- **文件头**：`X-Size` / `X-Sha256` / `X-Name` / `X-Rel-Path` / `X-Batch` / `X-Last` / `X-Batch-Size` / `X-Device-Name` / `X-Session` / `X-Session-Name`。
  头值只能 ASCII，所以中文名、相对路径、设备显示名与会话名统一 base64；发送前显式拒绝非 ASCII 或含换行的头。
  `X-Session` 是会话 ID（UUID 或设备 ID，本来就只有 ASCII），所以直接明文。
  `X-Device-Name` 与 `X-Session-Name` 都不参与签名，只用来给第一次出现的陌生会话起名（改名不该让旧请求失效）；
  老版本根本不发这两个头，名字退回设备 ID 的一截。
- **校验**：边流式写盘边算 sha256，与 `X-Sha256` 不符就删掉临时文件回 422，不留半成品。
- **路径守卫**：`X-Rel-Path` 只允许 `Component::Normal`，`..` / 绝对路径 / 符号链接组件一律 400。
- **大小上限**：`/msg` 1MB，单文件 8GB。聊天里的图片预览另有口径：≤4MB 自动出图，>40MB 不解图，
  引导用「在对比中打开」。
- **Windows 第一次监听会弹防火墙授权**，不点允许就对端永远发现不了本机（走手动 IP 也一样连不上）。

## 五、多台（≥3）怎么用

一句话结论：**三台同时往一台推可以；一台同时给多台推也可以，而且每台还能开好几个对话框；三台两两随时互发仍然做不到。**

为什么能“同时收”：`/ping` `/msg` `/file` 只校验口令签名，**不校验发送方是不是本机登记过的哪一台**
（`X-Device` 只是签名的输入之一）；接收端每个请求一个线程，批次状态按 `batch id` 隔离在
`Hub.batches`，所以多台并发推互不串，传大文件时别人的请求也进得来。口令对得上的来者就能发进来，
本机这边由 `ensure_session` 自动建会话并计未读 —— 没配对过也不丢消息。

为什么能“主动发多台”：`peers.json` 存的是数组，会话栏里每个框一行，发文字与发文件都发给**当前对话框**
那一台（`send_text(text, to)` / `send_paths(paths, to)`，`to` 是**会话 ID**，不传就取当前那个框；
发送时由它反查所属那台的地址）。没有群发：一条消息只落到一个对话框里，也不做中转。

### 拓扑得想清楚（三台两两随时互发做不到）

| 想要的效果 | 怎么连 | 结果 |
|---|---|---|
| 往主力机汇拢（最常见） | Mac 登记 B；C 登记 Mac | B↔Mac 双向可发；C 推给 Mac 不用登记也能发进来（自动建会话），Mac 要主动发给 C 得先把 C 登记上 |
| A、B、C 都要能主动互发 | 每台都把其它两台登记上（各自点一下候选或手动 IP） | 可以，但每台都得直接可达；没有中转 |
| 只在 A 上配一次对，B↔C 就自动通 | **做不到** | 心跳只 ping 本机自己登记过的那些对端，从不替别人转发 |

### 同一台开好几个对话框（多会话）

会话的主键是**会话自己的 ID**，不是对端 ID：

- 一台的**基础对话**直接拿对端设备 ID 当会话 ID。上一版根本没有 `sid`，老历史因此能不改写就归位（`Message::sid_of()`：`sid` 为空就按 `peer` 算）
- 同一台再开的框用另造的 UUID，由发起方生成
- 一个框在两边是同一个：发出去的每条请求都带 `X-Session`，对端按它分落点；在线态、地址、端口则统一取自**所属那台**（`Session.peer`），一台的几个框共用

入口只有一个：「＋ 新聊天」弹层里再点一次那台（名字上会写「已有 N 个，再开一个」）。
会话栏那一行只放「改名」与「删除」两个按钮 —— 栏子只有 214px，按钮再多名字就被挤没了；解绑也不在行上，
去「配对设置」里的「解绑当前对端」。要注意弹层只列已登记与刚发现的设备：那种只发过消息、还没登记的
对端（会话栏里有它一行但弹层里找不到），得先在「配对设置」里手填 IP 登记，才能在它身上再开框。
新框自动叫「设备名 · 月-日」（**本机的本地日期**，所以日期由前端算完传 `session_new(peer, name)`，Rust 侧只有 epoch 毫秒、算不出时区）。
同一天在同一台再开一个必然撞名，后端 `unique_name` 会加 `(2)`、`(3)` 区分（只在同一台范围内比）；
拿不到设备名（还没登记过的那台）就退回「设备名 · 话题 N」编号。想叫别的就点那一行的「改名」当场改。
**名字是建的时候定下、之后两边各改各的**：对方那个框改了名，不会把本机这行顶掉；反之也一样。

收到的消息归哪个框由 `resolve_incoming` 定，四条落点规则：

1. 没带 `X-Session`（上一版）、或带的就是发送方自己的设备 ID → 那台的基础对话
2. 本机已有这个会话 ID、且它确实属于这台 → 就用它（两边同一个框）
3. 本机已有这个会话 ID、但它属于**另一台** → 退回发送方的基础对话（不能拿别人的会话 ID 往别人框里塞消息）
4. 本机没有这个会话 ID → 认下来（对方先在自己那边开了个框，这边跟着建一个）

还有一种不进这四条的：`X-Device` 为空（认不出谁发的）既不新建也不归属，那几条只进「未标记」那一行看。

落点只看 `X-Session` 这个 ID，**不当名字当真**（名字是 base64、不签名、可以随便报）。
未读、分页游标、日期分隔线全部按会话 ID 各算各的，所以一个框翻到一半不影响另一个框。

### 首次准备清单

1. 每台填**完全相同**的配对口令（≥ 4 字符），设备名改成一眼认得出的（上限 40 字符）—— 设备名就是
   会话栏里那台**基础对话**那一行的名字（对端通过 `X-Device-Name` 报过来），同一台再开的框在后面添「· 月-日」。
2. **Windows 第一次监听会弹防火墙授权，必须点「允许」**。不点对端永远发现不了本机，走手动 IP 也一样连不上。
3. 每台的实际监听端口看连接面板。默认 45789，被占自动 +1，**三台端口很可能不一样**，手动 IP 时要填对。
4. 每台系统时间对齐。签名有 ±300 秒时间窗，超窗报的是「配对口令不匹配或时间戳超窗」，极易误判成口令写错。
5. 登记入口：会话栏点「＋ 新聊天」把候选与已登记的设备列在一起，点一台未登记的就是「配对 + 建基础对话 + 切过去」，
   点已经登记过的那台就是**在它名下再开一个对话框**；
   「配对设置」里点已发现的那行也可以；mDNS 被公司网络/VPN 屏蔽时直接走手动 IP。

### 两条纪律

- **别同名同时推。** 重名判定是「先看存在、再改名挪过去」，两台同一瞬间都推 `讲义.pdf`，
  其中一个挪不动会退回工位目录 `inbox/<UUID>/…`（文件不丢，但位置难看）。文件名带上设备前缀最保险。
- **删会话要先确认一次，而且不删历史。** 那一行的「删除」得连点两下：第一下只把按钮变成
  「确认删除？」（4 秒内不点第二下就复位）—— webview 里 `window.confirm` 不可靠，所以确认就地长在按钮上，
  与收藏视图的删除同一个口径。第二下只删**这一个对话框**与它的读指针：这个框会从列表里消失（会话 ID 记在
  `sessions.json` 的 `hidden` 里，不会被历史又补回来），同一台的其它框完全不受影响；
  以前发来的东西一条不少，对方在那个框里再发一条就自己回到列表。
  要真清掉历史，只能退出应用后手工删 `messages.jsonl`（不可恢复）。

### 连不上时的排查顺序

1. 状态条写「接收服务未启动」→ 端口 45789~45798 全被占，或防火墙没放行（原因原文会带在状态条里）。
2. 「已发现设备：无」→ mDNS 被屏蔽（公司网络/VLAN/VPN 的常态），直接走手动 IP，别等。
3. 「对端离线」→ 那台 app 没开，或 DHCP 换了 IP。点「配对设置」里的「重新探测在线」，不行就重填 IP。
4. 「配对口令不匹配」→ 先怀疑系统时间（±300 秒窗），再怀疑某台改了口令忘改其它几台。
5. 「还没添加这台，只能查看历史」→ 它给你发过消息所以会话在，但本机没有它的地址：
   在「配对设置」里手填它的 IP 登记一下就好（登记完它才会出现在「＋ 新聊天」的候选里，也才能主动发）。

### 多台是怎么落地的（以前这一节是「得动哪些地方」的 TODO）

- `Hub.peers` 是 `HashMap<设备ID, Peer>`，一台一个条目；`Hub.active` 存的是**会话 ID**，只是会话栏的焦点，**不是**发送目标（目标由命令参数 `to` 给）。
- 会话表以 `Session.id` 为主键：基础对话 = 对端设备 ID，新话题 = UUID。`session_create(peer)` 只能建基础对话（重复点不会多出第二个框），
  `session_new(peer, name)` 开新话题（名字由前端按「设备名 · 月-日」给，撞名时后端加 (2)；返回的 `active` 就是新框 ID，少一次往返），`session_rename(id, name)` 只改本机那一份，
  `session_focus(id)` / `session_delete(id)` 一律按会话 ID 走。
- 心跳用 `std::thread::scope` 并发 ping 每一台，逐台算 `online` / `last_seen`；
  `OFFLINE_THRESHOLD` 口径不变（3 秒一次 ping，连负 3 次判离线）。设备数按 ≤8 台设计，不设上限。
- `/ping` 不再对未登记者回 409，而是无脑回 200：口令对不对由发起方比对 `device_id` 自己决定。
  那个 409 是「只支持两台」时代的遗留，副作用是把第二个实例自报的端口丢掉了。
- 零配置仍然成立，但**不再“先绑定的赢”**：心跳 ping 通一台就直接登记它（可发），不占会话焦点。
- 入向消息的 `peer` 取 `X-Device`，再按 `X-Session` 过 `resolve_incoming` 定下归哪个框（四条落点规则见第五节）；
  陌生会话是在这里顺手建出来的，否则那条历史没人认领。
  收文件时先只算落点（`route_session`）给进度事件定归属，收完那一条才真正建框 —— 不该为一个没收完的传输先建会话。
- `msg_history(limit, before, session)` 是**先按会话 ID 筛、再定位游标切页**（先切后筛会让每页凑不满，游标还会串到别的框的历史上去）。
- 前端 `state` 按会话分组：每个会话 ID 一套 `stream/游标`（`state.cur` 也是会话 ID，不是对端 ID），心跳推的在线态由
  `syncRailFromStatus()` 按所属那台回填到它的每一个框，未读数只在 `sessions()` 里算（它要整读一遍历史，绝不能塞进每秒都可能推的 `status_json`）。
- 历史里的日期分隔线按**相邻消息**插，首屏 / 往前补页 / 新消息追加三处都要重算（`reconcileDividers()`）。
- 首次启动做一次迁移：`peers.json` 里每台各建一个基础对话、历史里露出的对端补在后头，读指针推到当下
  （免得第一次进来冒出一堆莫名未读）。老历史按它**当时落的 `peer` 值**分框：单台时期那个字段写的就是
  当时绑定的那台，所以基本正确；空值的进「未标记」那一行，只能查看、不能发、也不能删。
  ⚠️ `messages.jsonl` 原文不改写 —— 真实发送方无法回溯，不做猜测式修正。也正因为不改写，
  基础对话的会话 ID 必须等于设备 ID，否则那些没有 `sid` 的旧消息会找不到家。

## 七、几个反复踩过的点（改代码前先看）

1. **serde 字段一律 snake_case，不加 `rename_all`**。曾用 camelCase 序列化出 `dataUrl`，前端读 `data_url`
   拿到 `undefined`，表现是「图片解码失败」，排查成本极高。
2. **`input[type=file]` 在 WKWebView 里递出的 File 是 0 字节**（只能拿到名字/类型），所以选文件必须走 Rust 侧对话框。
   **paste 事件一样**：剪贴板里的文件/位图在 JS 里读不到内容，所以粘贴也只能在 Rust 侧读（clip.rs）；
   好处是拿到的是真路径，连文件夹都能粘。粘完把路径交给 `routeDrop`，跟拖拽走同一条下游。
3. **`hidden` 属性能不能生效取决于有没有 `.xxx { display: ... }` 盖住它**，style.css 里有一条
   `[hidden] { display: none !important }` 的统一规则，新增覆盖层时别再写高优先级的 display。
4. **拖拽遮罩必须 `pointer-events: none`**，否则会把 Tauri 原生 drag-drop 的 `drop` 事件吃掉。
5. **切视图时的 `clientWidth` 是 0**，隐藏期间不能做 fit 计算，要等 `onViewChange` 回来再重量一次。
6. 界面异常优先看日志：Rust 侧统一 `eprintln!`（`[net]` / `[xfer]` 前缀），前端 `console` 带 `[view]` 前缀。
7. 收到消息的 `peer` 字段存的是**签名里那个 `X-Device`（真实发送方的设备 ID）**，会话就按它归类。
   伪造这个头过不了签名，所以它能直信。两个例外：旧版 UI 拿不到名字时只能用一截设备 ID；
   **单台时期落的历史不可信**（当时写的就是接收那一刻绑定的那台），无法回溯修正，所以首次迁移只能按现值分（第五节）。
   同一台的几个框再按 `sid` 分；`sid` 为空的旧消息全部默认归到那台的基础对话（它的会话 ID 就是设备 ID）。
8. **clip.rs 的 Windows 分支在 mac 上只能靠壳工程做类型检查**：正式工程的 build.rs（tauri-build → winres）
   交叉到 windows 时要资源编译器（llvm-rc），本机没有，直接 `cargo check --target x86_64-pc-windows-msvc`
   会在 build script 里 panic。`tools/clip-win-check/` 就是为了绕过这一层：它用 `#[path]` 把 clip.rs 原样
   include 进来，再补 store / net::server 几个最小桩，依赖版本与正式工程一致：

   ```bash
   rustup target add x86_64-pc-windows-msvc
   cd tools/clip-win-check
   CARGO_TARGET_DIR=../../src-tauri/target cargo check --target x86_64-pc-windows-msvc --lib
   ```

   （共享 target 目录是为了重用已编好的 tauri 依赖，否则一次要重编几分钟）。
   这一步只保证能过类型检查，真正装包仍然只能靠 CI 的 windows 产物与实机验证。
9. **粘进来的图“显示不正常”，先查剪贴板再查代码**：源程序往剪贴板里放的可能就是它给这个文件画的
   **占位图标**（实测过一张 1024×1024 的“JPG 文档图标”位图，微信未下载完的图、云盘在线文件、
   网页里加载失败的 img 都是这个形状）。我们原样存进 pastebox，看上去就是“图错了”，其实链路全对。
   排查时靠只读探针（第六节）或 `osascript -l JavaScript` 列 `NSPasteboard.types` 看剪贴板内容，
   只看到 `public.png`/`public.tiff`、没有 `public.file-url`，
   说明源既没给路径也没给真图，改代码救不回来。
10. **Windows 的复制出口只挂了 CF_HDROP（文件），没挂图片位图**：mac 那份 PNG 是 NSBitmapImageRep
    现算的，Windows 要 CF_DIB 得走 WIC 解码，目前没有实机可验所以没写。
    影响：从我们 app ⌘C 出去再粘到 Windows 侧某些只收位图的目标会拿不到图（微信 Windows 版粘图文件会当文件发）。
11. **`public.file-url` 有两种给法**：有的来源只把它当**数据**写（`stringForType:` 返回 nil）。
    只读 string 的写法会把这种剪贴板误判成「没有文件」，退回去存那张**文件图标位图**，
    症状就是“粘出来的图永远是一个 JPG 文档图标”。现在 string 拿不到就按 UTF-8 解 data，
    两条路都空再兜一次 pasteboard 级的 `public.file-url`；备料用 `onlyfileurl.js`。
12. **微信网页版里“以文件形式发送的 JPG”，复制到的就是那张占位卡片**（实测）：
    浏览器里那张卡片本身就是一张 1024×1024 的图，⌘C 出去的就是它，
    跟本应用无关。判据：收到的文件名长成
    `_cgi-bin_mmwebwx-bin_webwxgetmsgimg__&MsgID=…&skey=…&mmweb_appid=wx_webfilehelper.jpg`。
    正确做法：先把文件**下载到本地**，再拖文件进窗口（或选中文件 ⌘C 后粘，走 file-url 分支拿原路径）。
    人肉判断口径：文档图标是“正方形 + 带 alpha + 四角全透明”，真照片与截图四角不会透明
    （实测：占位图 1024×1024 四角 alpha 全 0；真图 1234×1062 与截图 1059×549 四角均不透明）。
    程序里不再做这个自动识别（排障期加的 `looks_like_file_icon()` 与 `clip-note` 提示已拆）。
    **但先按 #14 排除“我们自己把有效 file-url 丢掉了”的情况** —— 四角透明的图标
    并不一定就是源的锅。
13. **早期版本会把收件箱消息的 `path` 按名字长度硬截**（还会削掉 `.jpg`），
    文件其实就在同一个目录里、只是名字更长，于是前端每次展开都报“缩略图读取失败”。
    现在启动时会跑一次 `Store::repair_inbox_paths()`：只认“名字≥ 100 字符 且
    同目录下恰好只有一个文件以它为前缀”这一种窄情形，找回就补写一条修正记录
    （JSONL 后写覆盖前写），幂等、不会把历史堆长。
14. **Finder 复制的文件，`public.file-url` 可能不是路径而是「文件 ID」**（本条才是“粘出来
    总是那张文档图标”的真凶）：长这样的 URL 直接取 path 会得到一个不存在的位置，
    于是被误判成“剪贴板里没有文件”，退回去存了随附的 `com.apple.icns` 图标：

    ```
    file:///.file/id=6571367.105483633
    ```

    认这种来源的特征：剪贴板类型里同时有 `com.apple.finder.noderef` / `fndf` / `com.apple.icns`。
    两层修法（`clip.rs`）：`resolve_id_url()` 走 `NSURL.filePathURL` 把 ID URL 转成真实路径；
    转不动再兜一层 `nsfilenames_paths()` —— 把已废弃但 Finder 仍在写的 `NSFilenamesPboardType`
    （一份字符串数组 plist）用 `NSPropertyListSerialization` 解出来。
    验证：只读探针在真实现场上拿到了完整中文长路径（`/Users/…/详情_13_副本2.jpg`）。
    注意：转完就是现成的文件系统路径，**不能再走一遍百分号解码**，否则中文会被拆坏。
15. **“点了 B 却粘进 A”：两层叠加的坑，只修一层不够**。
    第一层：单击空窗那条传了 `pane.key`，进的是点的那个窗；而全局 `⌘V` 走
    `routeDrop(paths)`，**不携带落点**，`registerDropHandler("compare", …)` 拿到
    `paneKey === undefined` 就退回 `fillPanes(paths, null)` —— 而它从第一个空窗开始铺，于是永远就是 A。
    第二层（只修第一层时会残留）：空窗单击处理里 `if (pane.loaded) return;` 写在最前面，
    **点一个已有图的窗格时连“选了哪格”都没记**，于是 ⌘V 依旧拿不到目标。
    定稿（`view-compare.js`）：`panePicked` 与 `activePane` **分开记**（`assign()` 也会改
    `activePane`，光靠它分不清“用户选的”还是“刚被自动铺上的”）；单击先 `setPicked(pane)`
    再判断是否空窗；`pasteTargetKey()` 优先给 `panePicked`（**已有图也照换**，换掉就是点的意图），
    被布局切走或从未点过才退回“第一个空窗”；拖拽有真实落点时仍按落点。
    选中格原先描一圈蓝边（`.viewport.is-picked`）；**那圈边已按用户要求拆掉**（压在图上太抢眼），
    类名仍挂在 DOM 上当 devtools 标记，路由靠 `panePicked`，与样式无关。
16. **算“图片”的扩展名有三份表，加一种格式必须一次改齐**：Rust 的 `IMAGE_EXTS`（`list_folder_images`
    的目录过滤与 `pick_images` 对话框的 filter 都用它）、`lib.rs` 的 `mime_of()`（认不出就回
    `application/octet-stream`）、前端 `api.js` 的 `IMAGE_EXT`（粘贴、外部打开、侧栏的二次筛共用一份）。
    不齐的症状很隐蔽：侧栏列得出这张图、点进去却报「解码失败」（tif/tiff 就是这么补进来的）。
    `tools/folder_browse_check.mjs` 里「tif 也认（三份表必须一致）」与「后端漏进来的非图片会被前端
    再筛一道」两条专门盯这件事。
17. **「哪些窗可见」只有一个口径：`LAYOUT_KEYS`，而它必须与 CSS 的 `body.layout-N` 类同改**。
    可见性在两处各自表达：JS 里 `visiblePanes()`（同步广播、找空位填充、粘贴落点全问它），
    style.css 里靠 `body.layout-1/2/4` + `.only-multi` / `.only-grid` 准入类控制显隐。只改一边
    的症状很难查：要么图窗在 DOM 里可见却进不了同步组，要么反过来 —— 一个看不见的窗接收了
    `⌘V`，用户只觉得「粘不上」。`body` 默认就是 `layout-2`（HTML 里写死）而不是靠 JS 加类，
    否则首帧会闪一下。`tools/prefs_layout_check.mjs` 第 9 节专门核这份合约（假 DOM 不解析 HTML，
    所以那一节是对源码做字符串核对，而不是跑事件）。
    **准入类如今只剩窗体自己用**：`#pane-b` 带 `.only-multi`、`#pane-c/d` 带 `.only-grid`。
    工具栏（「打开 A/B/C/D」已拆）与状态栏（四个窗的信息行已搬进窗里，见 #21）都不再需要准入规则 ——
    留着不删不会报错，但下一个人会照着它再开一个「只能露一半」的入口出来。
18. **「工具栏一个开关、设置里又一个开关」这种需求，联动要拆成「镜像」与「动作」两件事**：
    程序化地改 `checkbox.checked` / `select.value` **不会触发 change 事件**，所以互相回填不会自己转回去，
    但也意味着镜像那一半不会顺手执行动作 —— 每个入口都得自己把「改取态 + 执行动作 + 存盘」三件事写全。
    另外这枚开关是**真 `input` 藏在 `label.switch` 里**（`input` 本身 `display:none`），光靠 `:disabled`
    看不出任何区别，得给外层 label 另挂一个 `.is-disabled`（含 `pointer-events: none`），
    并靠 `chk.closest(".switch")` 找到那一层。
19. **存盘只看「真的改了吗」**：`setLayout()` 返回布尔，调用方（三档按钮 / 抽屉下拉 / 快捷键）写成
    `if (setLayout(k)) savePrefs({ layout })`。无条件存盘的话，重复点当前那一档也会写一次盘。
    非法值同理：前端 `LAYOUTS.includes` 先拦下（比丢给后端报错更严，磁盘上永远不会有非法布局），
    但拦下后必须 `refreshLayoutUI()` 把下拉取态拉回真实那一档，否则控件会停在一个界面根本没进入的档位上。
20. **“选中即显示”之后，重复指向同一行的入口必须短路**：侧栏的入口从“只有点行”变成了“点行 + ↑↓ + Home/End + Enter”，
    同一个 `browseTo()` 会被重复调到同一行。不拦住的话两图下会“把同一张塞进对面窗”（症状就是莫名多出图），还白读一回盘。
    判定不能只看游标 `browse.idx`，要同时比对**可见窗**里的 `p.meta.path`：中途手动换过图、或那张推到了隐藏窗，
    游标都是陈的，此时必须重新读一次。

21. **每个窗的信息就该住在自己那个窗里**：四个窗的「文件名 · 分辨率 · 体积」原先挤在窗口底部
    那条共用状态栏（`.statusbar`）里，两个毛病：一排平排四列时宽度不够，只能裁成「2048×…」；
    而且对不上是哪一格的数。现在每个 `<section class="pane">` 底部多一行 `.pane-foot`（id 仍是
    `st-info-a/b/c/d`，`refreshStatus()` 一行没改），宽度天然跟着窗走，也就自然跟着分隔条与网格列宽变。
    搬进窗里还顺手把 #17 那个「准入必须与窗同档」的问题消灭了 —— 脚注在窗内部，窗藏了它跟着藏，不再需要准入类。
    构造上的两个必需项：`.pane` 要从横向 flex 改成 `flex-direction: column`（`.pane-tag` 是绝对定位，不受影响），
    并且给 `.viewport` 补 `min-height: 0`，否则画面会把脚注顶出窗外。

22. **列表里的名字要从中间裁，不能只靠 CSS 的末尾省略号**：文件浏览器的名字往往是「公共前缀 + 随机尾巴」
    （UUID、微信哈希、`..._2K_20261025150443.jpg` 这种带时间戳的生成图），末尾省略号恰好把**区分点**和扩展名
    一起切掉，两行看着完全一样。所以显示前先用 `shortName()` 压到 `STRIP_NAME_MAX` 个字符：保住开头一半、
    尾部一半与末尾那段扩展名（只认点后 ≤ 8 字符的，`image.png_2K_xxx.jpg` 这种点在中段的也能认对），
    CSS 的 `text-overflow` 降级成窄侧栏下的最后一道保险。裁的只是那一行显示文本 ——
    `title`、`dataset.path`、排序、落盘路径全部用完整名，不然悬停与后续定位都会错。

23. **侧栏那 190px 以前根本没生效**：`.filmstrip` 写的是 `flex: 0 0 190px`，但它是 flex item 而 **flex item 默认
    `min-width: auto`**，里面 `.fs-name` 又是 `white-space: nowrap` —— 于是侧栏的自动最小尺寸等于
    「最长那条名字不换行的宽度」，190px 被撑到几百 px，名字多长都完整显示，CSS 的省略号永远不触发。
    症状上看不出错（不报错、不错位，只是宽），只能从「为什么定宽栏里的长文本从不被裁」这个角度反推。
    修法是给 `.filmstrip` 补 `min-width: 0`（与 `.fs-main`、`.cmp-body` 上已有的那几条同一个道理）。
    **同一个坑的第二个症状**：修完之后名称列真的只剩 ~102px 了，`shortName()` 若还按 24 字符裁，
    会被 CSS 末尾省略号再补一刀，恰好把中间裁切想保住的扩展名砍掉 —— 所以上限要按**列实宽**定（16），
    并把 `.fs-name` 降到 12px 让这 16 字符刚好放进去。两条都已入合约断言（`prefs_layout_check` 第 9 节）。

24. **「一个 item 挂两味」不能写成「两个 item 各挂一味」**：⌘C 复制一张图出去会变成两张一模一样的图，
    原因在 `clip.rs` 的 `copy_as_file`：它把 NSURL 与一个只带 `public.png` 的 item 一起交给
    `writeObjects:`，而 **`writeObjects:` 是一个对象一个 pasteboardItem** —— 剪贴板里于是有 2 个 item。
    只认第一个表示的应用（微信聊天框、Finder）看起来完全正常，**逐项粘**的应用（Word / 备忘录 / Keynote）
    会把文件与位图各插一张，看起来就是「复制出来两张同样的图」。
    修法是把两味合并到**同一个** `NSPasteboardItem`（`public.file-url` 的数据就是 URL `absoluteString` 的
    UTF-8 字节，`public.png` 直接 `setData:forType:`），解不出位图时才退回纯 NSURL。
    **为什么原来的自检没发现**：`osascript` 列的是 pasteboard 级的 `types`，它把所有 item 的类型拉平去重，
    两味分在两个 item 上时看起来完全一样。所以探针（`clip::real_clipboard::真机剪贴板探针`）现在直接
    `dump_items()` 数 item 个数，并**回读一次**确认合并后文件那味仍解得开（我们自己读剪贴板走的也是 `public.file-url`）。
    另一件同症状的不同事：`copyTargets()`（⌘C 拿哪几张）以前不去重，同一张摆在两个窗里时会把同一条路径
    复制两遍，粘出去也是两张一样的图 —— 现在过 `new Set`，第 14 节看着这条。

25. **「解绑」得配一份名单，否则只撑一秒**：症状是点了「解绑当前对端」，几秒后那台又自己连上了。
    原因不在解绑那一下，而在心跳线程（`client.rs::spawn_heartbeat`）：它每秒把**所有还没登记的 mDNS 候选**
    都 ping 一遍，ping 通就 `bind_peer` 自动登记 —— 而 mDNS 不会因为本机解绑就停止广播，那台依旧在候选里。
    所以解绑时要把设备 ID 记进 `peers.json` 的 `ignored`（与 `sessions.json` 里那份 `hidden` 同一个思路），
    心跳的候选过 `auto_bind_targets()` 时同时排除「已绑的」与「解绑过的」。
    **名单必须落盘**：只在内存里拉黑，重启后 `Hub::new` 什么都不知道，那台又被自动登记回来了。
    两个口径得跟着对上：① 它仍然留在「已发现」候选里（要恢复只能用户亲手点，但得看得见），
    候选按钮上标一句「已解绑」；② `bind_peer` 会把它从名单里拿掉 —— 手动 IP、点候选、重新探测
    都算用户亲手重新添加。另外 `startChat()` 里「先添加再开框」那一步原本写在 `have` 分支之后，
    于是一台**已有历史框**的解绑设备会被直接开出新框而跳过添加，变成一个永远发不出去的框 —— 现在提到最前。

26. **对端备注名（像微信那个）：口径只有一份，而且不能上线**：`Peer.alias` 只存本机，
    空串 = 没备注。显示一律走 `Peer::display_name()`（备注 > 对方报的名 > 露一截设备 ID），
    前端 `peerLabel()` 逐字抄的是同一个口径 —— 两边不一致就会出现「顶栏叫备注、会话栏叫设备名」。
    三个必须防住的坑：
    ① `bind_peer` 是**整条覆盖**，而对方 `/ping` 响应里根本没有 `alias` 这个字段，
    不从旧记录里把它搬过来，心跳每一拍都会拿对方报的名把用户刚写的备注顶掉（症状是「改完几秒就恢复原状」）；
    ② 备注改了但会话栏里还是老名字等于只改了一半：`set_peer_alias` 会把这台名下**还叫旧显示名**的
    对话框一起改名（`rename_by_display`），但用户自己改过名的框（「报销单」）与按日期起的名不能跟着动 ——
    那是他给这个框起的名字，不是一台设备的名字；③ 心跳每秒都可能推一次 `peers-changed`，
    备注框的回写要过三道判断：焦点在里面不动、框里是一份**未保存的草稿**（与代码上次写进去的那份不同
    且后端没变）也不动，只在「换了那一台」或「后端那份真变了」时才回写 —— 只判 `document.activeElement`
    还是不够，用户点去别处一下草稿就没了。
    老 `peers.json` 少 `alias` / `ignored` 两个字段都靠 `#[serde(default)]` 兜着，不会整个对端列表读不出来。

## 八、对比视图：浏览整个文件夹（前后两张同时在屏上）

**列表来源只有一个：当前这张图所在的目录。** 没有另做「打开文件夹」对话框 —— 任何途径
（⌘O、单击空窗、拖文件进窗、⌘V 粘、系统「打开方式」、收藏与传输里的「在对比中打开」）
载入一张**带本机路径**的图，都会汇到 `fillPanes()` 末尾那唯一一处接线（`noteLoaded()`），
由它调 `ensureFolderList()` 列出那个目录里的全部图片，左侧的浏览侧栏随即露出来。所以：

- 只有名字没有路径的来源（浏览器兜底、`input[type=file]` 递出的 0 字节 File）列不出东西，
  侧栏保持收起，并在提示位原文写「这个来源没有本机路径，列不出文件夹」，不假装「目录里没有图」。
- 同一个目录不重发 IPC，只把当前项对齐；换了目录才重新列一次，并清掉上一目录的小图与失败记录。
- Rust 只回原始条目（不排序），**自然序在前端做**：`localeCompare(name, "zh-Hans-CN", { numeric: true, sensitivity: "base" })`，
  天然得到 `IMG_2 < IMG_10 < IMG_100`，不需要在 Rust 里手写数字比较。
- 递归子目录、循环浏览、把 ⌘O 多选那几张当队列、传输/收藏视图里的浏览入口 —— 本轮都不做。

**落窗严格交替**（只对两图/四图布局）：`browse.slot` 记的是**上一次落在哪个窗**，下一次浏览就去对面，
所以第一次浏览绝不会把刚手动打开的那张顶掉；`btn-clear` 清空后从 A 起（它只清高亮与游标，
列表保留，因为目录还是那个）。四图布局下浏览只在 A/B 之间轮转，**C/D 不参与**（那两格留给用户自己摆参照图）。
**单图布局下这条规则整体不适用** —— 只剩 A 一个窗，没得对面可去，`nextBrowseSlot()` 直接回 `"a"`，
点一行 / 按 `[`/`]` 就是换掉那一张（状态条也只写「第 N/M 张」，不再提「另一窗留着上一张」）。
读失败（文件被移走/改名）时**既不动 slot 也不推进游标**，只把那一行标灰 —— 对照位不能被一次失败的浏览悄悄换掉。

**键盘选中即显示**（`↑`/`↓`/`Home`/`End`）：这三个键与点行汇到同一个 `browseTo()`，
所以“在左侧选到哪一行”与“右边正在看哪一张”永远是同一件事，不存在“选中了但没显示”这种中间态。
行上因此也**只留一层视觉状态**：`.fs-row.is-current` 的底色 + 左侧那根竖条。原先 `.is-sel` 还会另描一圈
`inset` 框，↑↓ 改成选中即显示后两者永远落在同一行，那圈框纯属重复描边，已按用户要求拆掉
（类名仍挂在 DOM 上，自检的 `selIndex()` 与 devtools 靠它读“选中在哪一行”）。
侧栏本体（`<aside tabindex="0">`）也不再画焦点框：原先是 `.filmstrip:focus-visible { outline: 1px solid }`，
现已换成写在 `.filmstrip` 上的 `outline: none` —— **只删那条规则是不够的**，点行与 Tab 进来都会走
`focusStrip()` 的程序化 `focus()`，拆了自定义样式只会让 UA 默认焦点环冒出来，症状看着一模一样。
这三个键另外还会走两道**短路**（都在 `browseTo` 开头）：
- **已经在看这一行**（顶到首尾再按、`Enter`/`Space` 确认都会走到）：`index === browse.idx` 且这一张**确实还画在某个可见窗里**
  （比对 `p.meta.path`，不能只看游标 —— 中途 ⌘O 手动换过图时游标还是旧的，落在隐藏窗里也算没在看）才直接返回。
  不短路的话，两图下会把同一张再往对面窗塞一次（看着像“莫名多出图”），还白读一回盘。
- **连按方向键**：上一张还在读时 `browse.inflight` 占着，新按的那一行记到 `browse.wanted`（只留最后一个），
  这趟读完再追一次 —— 合并的是**显示**（中间那几张不停下来看），不是丢请求（每张该读的都读了）。
  那一次没读成也要把 `wanted` 作废，否则下一次浏览会莫名跳到陈旧的一行。

**「对齐」靠的是已有的同步模式**，浏览这一层没有新发明：`Pane.setImage()` 里新载入的窗会沿用参照窗的
`scale/x/y`，所以前后两张自动停在同一区域，翻着翻着不会越看越歪。

### 为什么侧栏不是一片真缩略图

项目**刻意不引入 `image` crate**（`Cargo.toml` 里连 arboard 都关了默认特性，就是为了不把整套图片解码依赖
拖进来），Rust 侧出不了真缩略图；而 `read_image` 回的是**整图 base64**（上限 80MB），一个目录几百张绝不可能
一次全读。所以小图就是「整图 data URL + CSS 缩到 40px」，靠四道闸门压住内存（常数集中在
`view-compare.js` 的 `STRIP_*`，要调就改那一块）：

| 闸门 | 值 | 意思 |
|---|---|---|
| `STRIP_DECODE_WINDOW` | 1 | 只自动解**当前项 ±1**（≤ 3 张）。`IntersectionObserver` 只用来**摘掉滑出视口的位图**；滚进来的行只要在窗口外也不去读盘 —— 内存上限只看当前项 ±1 那三张，不看窗口里画了多少行 |
| `STRIP_AUTO_MAX` | 4MB | 与传输视图 `PREVIEW_AUTO_MAX` 同口径：过大的不自动解，行上只给一个「大」字占位，要让这一行显示出来（点行 / ↑↓ 选中 / `[`/`]`）才走一次 IPC |
| `STRIP_LRU_MAX` | 8 | 内存里最多留 8 张整图 data URL（拿 `Map` 的插入顺序当 LRU：命中就重插到末尾，最老那张连同它画出来的位图一起丢） |
| `STRIP_INFLIGHT_MAX` | 3 | 同时发出去的 `read_image` 封顶 |

两个顺手省盘的细节：`browseTo()` 载入大图成功后会把那份 data URL **塞进 LRU**，所以点一行只读一次盘，
不会大图小图各读一遍；换目录时 `buildStrip()` 先 `stripIO.disconnect()` 再重建行，否则换过几个目录后
观察名单会把已被拆掉的旧节点一直强引用着。

真要一片满屏真缩略图，两条后续路（本轮都不做）：Rust 侧生成 128px 缩略图 + 磁盘缓存；
或启用 Tauri 的 `asset://` 协议（要同时改 CSP 与 capability，第二节的权限声明那块）。

### 行上的名字：从中间裁，不是从末尾裁

侧栏那一列只给 `STRIP_NAME_MAX = 16` 个字符，超出由 `shortName()` 从**中间**裁：
`Generate_Amazon_background_image_2K_20261025150443.jpg` → `Genera…50443.jpg`。
为什么不用纯 CSS 的 `text-overflow: ellipsis`（它一直在 `.fs-name` 上，但只在名字比列宽还宽时才兜底）：
这类图（UUID、微信哈希、带时间戳的生成图）开头一个样、区分点全在尾部，从末尾裁会把时间戳和扩展名
一起吃掉，两条微信图会被裁成一模一样。裁的只是显示文本，`row.title`（整条路径）与 `dataset.path` 都是完整的，
悬停能看全；`tools/folder_browse_check.mjs` 第 13 节拿用户实拍那几条名字核了具体的裁法。

16 这个数是按列实宽定的，不是拍脑袋：侧栏 190px 扣掉 padding、序号、小图与两个 gap 后只剩 ~102px，
`.fs-name` 因此降到 12px（body 继承下来是 13px）让 16 字符刚好放进去。前提是先给 `.filmstrip` 补上
`min-width: 0` —— 没这句时侧栏会被 nowrap 的长名字撑到几百 px，定宽与裁切全部白做（#23）。

几个样本的裁法：`image.png_2K_20261025174057.jpg` → `image.…74057.jpg`、
`WeChat4dfa9b61996222cdb06be62a8a5b85d09.jpg` → `WeChat…85d09.jpg`、
`f6fd84b2-b8c0-418e-ab62-441064623d64.jpeg` → `f6fd8…23d64.jpeg`；16 字符以内的（`IMG_2.png`）一字不动。

### 结构上唯一一处不能改的地方

侧栏是 `<main class="stage">` 的**兄弟**而不是子元素，两者一起包在新加的 `.cmp-body` 里。
原因：分隔条按 `ui.stage.getBoundingClientRect().width` 算百分比并写 `flex: 0 0 x%`，
侧栏挤进 stage 会让两窗总宽溢出、拖拽比例全错。包一层则分隔条逻辑一行都不动。
收起只靠 `hidden`（style.css 里那条 `[hidden] { display: none !important }` 统一规则），别再写高优先级的 display。

### 已知边界

- 目录里只有当前这一张：列表照常显示（就一行），`[`/`]` 只会说「已经是第一张/最后一张（共 1 张）」，不循环。
- 后端封顶 `FOLDER_MAX_ITEMS = 2000`，`truncated` 字段跟着回，前端在列表底部写「目录过大，只列出前 2000 张」。
- **iCloud「优化存储」的文件**：`std::fs::read` 会触发按需下载，症状是点侧栏某一张长时间停在「读取中」
  （小图那趟 `read_image` 失败还会把那一行标灰）。这不是链路坏了，先在 Finder 里把那张图下载到本地。
- `Esc` 只在**焦点在侧栏上时**收侧栏；放大层打开时 Esc 仍先关放大层，这个优先级没动。对比视图里还多一层：**设置抽屉开着时 Esc 先收抽屉**，才轮到侧栏。
- 用户自己收过一回侧栏（`⌘⇧B` 或行尾那个「×」）就不再自动弹出来抢地方，直到他再按一次开关。

## 九、系统设置与三档布局

设置只有**三项**，而且只有对比视图用：显示几张图、是否同步、滚轮/触控板双指干什么。
前两项是**一处设置两个入口**（工具栏 + 抽屉），滚轮行为**只剩抽屉一个入口**（工具栏那枚已按用户要求撤掉）；状态一直只有一份。

| 项 | 工具栏 | 「设置」抽屉（`#cmp-settings`） | 快捷键 |
|---|---|---|---|
| 显示图片数量 | 只有 `1 图` / `2 图` 两枚分段按钮（**四图 2×2 不在工具栏上**） | 下拉「显示图片数量」（三档都在） | `3` / `2` / `4` |
| 图片同步 | 「同步」开关（`#chk-sync`） | 开关「图片同步」（`#chk-set-sync`） | — |
| 滚轮行为 | **工具栏上没有这一枚**（`#sel-wheel` 已拆） | 下拉「滚轮 / 触控板双指」（`#sel-set-wheel`，**唯一入口，也是真值所在**） | — |

任一处改动都**只传改动那一项**写盘（`set_prefs` 里未传的字段保持磁盘原值）。
滚轮的真值现在存在抽屉那枚下拉上，读它的只有一处 —— `wheelMode()`（`view-compare.js`，与 `isSync()` 同一个写法），
`currentPrefs()` 与滚轮监听都走它。拆工具栏那枚时只删 HTML 是不够的：`ui` 里的 `wheelSel` 引用、
两个入口的互相回写、以及滚轮监听里那句 `ui.wheelSel.value === "pan"` 都得改成读 `wheelMode()`，
否则滚轮会默默固定在默认那一档。
抽屉本身不是设置、只是一个覆盖层：工具栏 `#btn-cmp-settings` 负责开合与高亮，Esc 或抽屉里的「收起」（`#btn-set-close`）关掉 ——
**高亮与开合走同一个入口 `setSettingsOpen()`**，否则抽屉收起来了、工具栏那枚还会长亮着。

### 三档布局分别是什么

| 档 | 可见窗 | 落窗规则 | 备注 |
|---|---|---|---|
| `1` 单图浏览 | A | 点列表行 / `[`/`]` **就换掉那一张** | 只剩一个窗，「同步」两个入口一起禁用（灰掉 + `pointer-events: none`），状态不丢，切回多窗又生效 |
| `2` 两图并排（默认） | A / B | 严格交替（第八节） | 唯一能拖分隔条的一档 |
| `4` 四图 2×2 | A / B / C / D | 浏览只在 A/B 轮转，C/D 不参与 | stage 是 grid，分隔条收起 |

布局不只是一个布尔开关：以前是「网格 / 不是网格」两态（`grid-mode`），现在是三态，
JS 里 `LAYOUT_KEYS` 与 CSS 里 `body.layout-1/2/4` 共同承担可见性（同改约束见第七节第 17 条）。
「浏览一张图片」做成**一档布局**而不是一个临时模式（已确认）：它跟 2/4 图是同一个轴上的三档，
而不是另一套正交开关，否则要多面对「单图模式下选了 4 图」这种组合。

### 存了什么、什么时候写

- `prefs.json` 就三个字段：`layout` / `sync` / `wheel`（Rust 侧 `Preferences`，`store.rs`）。命令也只有两条：`get_prefs` / `set_prefs`（`prefs.rs`）。
- 出厂态：两图 + 同步开 + 滚轮缩放，与 HTML 里写死的那一份一致；**首启动不会自动写一份文件**。
- 读只读一次：模块加载末尾的 `loadPrefs()`，异步 —— 所以首帧按出厂态排布，读到存的那一档再切过去。
  这就是 `body` 要带 `class="layout-2"` 而不是等 JS 加类的原因，不然 B 窗会先被藏一下再露出来。
- 非法值在进后端前就被前端拦下（`LAYOUTS.includes`），`set_prefs` 自己也会 `Err`；
  手改坏的 `prefs.json` 则由 `normalize()` 退回默认，不会把界面带进一个没有 CSS 的布局（那比退回默认难查得多）。
- 非 Tauri 环境（浏览器直开 `js/index.html` 调试）两条命令都挂，一律当「存不上」处理：界面照常可用，只是下次启动回到出厂态。

### 已知边界

- 「同步」只管缩放平移一致，**不影响哪张显示在哪个窗**；单图下它没有作用对象，所以是禁用而不是隐藏（用户得知道为什么不能点）。
- 侧栏的开合状态、分隔条拖出的窗格比例都**不进 `prefs.json`**（那是单次会话自己的事；切布局时还会把 inline flex 抹掉）。
- 窗不可见时不会把图塞到一个看不见的窗里：`fillPanes()` 会把这种落点降级成可见窗（「打开 A/B/C/D」 四个入口已拆，现在指定落窗只剩「单击那个空窗」，而空窗本来就是可见的，所以这条降级如今只是防御）。
- **工具栏上没有 `打开 A/B/C/D`，也没有「4 图」那枚按钮**（用户要求）：要往指定窗里放图就单击那个空窗（先试粘剪贴板、没图才弹选文件，落点就是点的那格）、拖文件进窗，或者 ⌘V；一次多张走「打开对比」（⌘O，自动铺满可见窗）。四图布局只能从设置抽屉里选（快捷键 `4` 仍可用），所以**四图下工具栏那两枚都不亮**，取态看抽屉里的下拉。
- `tools/prefs_layout_check.mjs` 的假 DOM **不解析 HTML**，所以显隐那部分不是真渲染，
  而是对 `style.css` / `index.html` 源码做字符串核对的「合约」（那一节的第 9 部分）；真机目视仍然必要。
